## 1. 总览与架构

pi0.5 是 PaliGemma（视觉-语言）+ Gemma Expert（动作）的双模型架构，动作空间为**全身 34 维笛卡尔 SO3**。微调链路：

```
真机遥操作采集 ──> 原始 HDF5（官方格式，含底盘/力矩/三相机）
                        │
                  标注（语言指令 + 成功标签）
                        │
        convert_hdf5_to_lerobot ──> LeRobot 数据集（笛卡尔 SO3 + 视频）
                        │
              compute_norm_stats ──> norm_stats.json
                        │
                   train.sh ──> checkpoint（含 processor + 权重）
                        │
        ┌───────────────┴───────────────┐
   serve_policy（推理服务, WebSocket）        │
        │                              评测客户端
   真机 astribot_eval / 仿真评测 ──> 成功率
```

**关键前提：数据是一切。** 模型能否学会取决于数据的**任务一致性**与**分布多样性**——物体位置、初始条件必须充分随机化，否则模型会走"记忆平均动作"的捷径而忽略视觉（因果混淆，见 [第 11 节](#11-已知坑与解法)）。

## 2. 环境搭建

训练环境独立于机器人控制环境（避免 PyTorch 版本冲突）。

```bash
# Python 3.11 + CUDA 12.1+（推荐 12.4）
conda create -n astribot_pi05 python=3.11 -y && conda activate astribot_pi05
cd <astribot_pi05 仓库>/astribot_pi05
bash install.sh          # 装 torch2.7 + transformers 补丁 + flash-attn（尽量装上，省显存）
```

**境内网络两项必做：**

1. **tokenizer 离线化**。训练/推理要加载 `google/paligemma-3b-pt-224` 的 tokenizer，境内直连 HuggingFace 常超时。从魔搭下载：

   ```bash
   pip install modelscope -i https://mirrors.aliyun.com/pypi/simple/
   python3 -c "from modelscope import snapshot_download; print(snapshot_download('AI-ModelScope/paligemma-3b-pt-224', allow_patterns=['tokenizer*','*.json','special_tokens*']))"
   export HF_HUB_OFFLINE=1      # 训练/推理都要
   ```

   > ⚠️ **不要把下载目录硬编码进 `processor_pi05.py`**。早期这么干过，结果换机器/换账号就崩，且报错发生在 processor 构造阶段很难定位。正确做法是应用本仓库的补丁
   > `patches/0001-tokenizer-path-resolution.patch`，它把 tokenizer 来源改成四级解析：
   > `tokenizer_path` 参数 → 环境变量 `ASTRIBOT_TOKENIZER_PATH` → 本地常见位置（`~` 展开，对任何用户成立）→ 回退 hub id。
   > 之后换机器只需 `export ASTRIBOT_TOKENIZER_PATH=<含 tokenizer.model 的目录>`。细节见 `patches/README.md`。
   >
   > 顺带一个事实：官方 `pi05_pnp` checkpoint 自带的 `processor/tokenizer.model` 与魔搭副本 **md5 完全相同**，可互换。

2. **ffmpeg**（视频编码要用，转换与训练都依赖）：

   ```bash
   conda install -n astribot_pi05 -c conda-forge ffmpeg -y
   ```

## 3. 数据采集

### 3.1 任务设计原则

- **单批一个任务**。一批数据对应一个明确任务（如 "pick up the red cube and put it in the box"）。多任务分批采、或用逐段标注（[第 4 节](#4-数据标注)）。
- **充分随机化**。每条 episode 换物体位置、初始姿态、光照等。分布越窄，模型越容易忽略视觉去背平均动作。**这是模仿学习最常见的失败根因**，务必重视。
- **数据量**。单任务微调建议 ≥ 50 条成功演示，100+ 更稳。

### 3.2 遥操作采集

用官方 `astribot_eval/tools` 的遥操作工具（VR / 手柄）完成任务，每条录一个原始 HDF5。采集时机器人本体电脑运行官方采集链路。

### 3.3 原始 HDF5 格式

官方采集产出的 HDF5 结构（关键部分）：

| 组 / 键 | 形状 | 含义 |
|---|---|---|
| `poses_dict/astribot_<部件>` | (T,7) | 各部件**实际**笛卡尔位姿（xyz + 四元数） |
| `command_poses_dict/astribot_<部件>` | (T,7) | 各部件**指令**位姿 |
| `joints_dict/joints_position_state` | (T,25) | 关节实际位置（含底盘 3 + 头部 2） |
| `joints_dict/joints_position_command` | (T,25) | 关节指令位置 |
| `images_dict/{head,left,right}/rgb` | (N,) | 拼接 JPEG 字节流 |
| `images_dict/{head,left,right}/rgb_size` | (T,) | 每帧 JPEG 字节数 |
| `endpoint_wrench_dict/*` | (T,6) | 末端力/力矩 |
| attrs `episode_success` | - | 成功标签（可选，见 4.3） |

## 4. 数据标注

官方 `convert_hdf5_to_lerobot` 有两种标注模式。**语言指令**是 episode 级（或逐段），**成功标签**在 HDF5 attr。

### 4.1 模式 A：整批一个任务（推荐，零标注量）

单任务重复采集用这个——`--coarse-prompt` 给一句话，对所有帧写同一 prompt，不需要任何标注文件：

```bash
python3 -m pi05.tools.convert_hdf5_to_lerobot \
  --raw-path <raw_dir> --output-path <out> --dataset-name my_task \
  --coarse-prompt "pick up the red cube and put it in the box" \
  --fps 30 --robot-type S1-stationary
```

### 4.2 模式 B：逐段标注（多任务 / 子任务）

不给 `--coarse-prompt`，转换器会去 `raw_path/Labels/` 找 JSON 标注（Label-Studio 风格：`videoFrameTool` 打关键帧 + `textTool` 写整段 coarse prompt）。每个关键帧标 `Arm`/`Object`/`Action` 三属性，转换器用内置 `ACTION_DICT`（`grab→"pick up the {}"`、`place→"place the {}"` 等）自动拼 fine prompt。适合长程 / 多子任务演示。

### 4.3 成功标签

成功标签不在 JSON，而在 HDF5 attr **`episode_success`**（转换器 `get_episode_success_flag` 读它：>0 记成功，默认 1）。两种做法：

- **筛选式（简单）**：只留成功演示，不设 attr（默认全成功），失败的直接删源文件。
- **显式标注**：审查后给每条写 attr：

  ```python
  import h5py
  with h5py.File(path, "r+") as f:
      f.attrs["episode_success"] = 1   # 或 0
  ```

## 5. 数据审查与筛选

转成 MCAP 在 [Foxglove](https://foxglove.dev) 里逐条审查（三相机画面、关节曲线），把抓空/滑落/异常的删掉。本仓库提供 `convert/official_hdf5_to_mcap.py`：

```bash
pip install mcap h5py numpy opencv-python
python convert/official_hdf5_to_mcap.py --src <raw_dir> --out ./mcap
# Foxglove 打开 .mcap：/camera/head|left|right 看画面，/joints/state 画关节曲线
```

对模仿学习，"标注是否完成"本质上就是**筛选出成功演示**——留下的即成功集。

## 6. 转换为 LeRobot 格式

用官方转换器（[4.1](#41-模式-a整批一个任务推荐零标注量) 命令）。它做三件事：写 prompt 到 HDF5 → 逐帧组装 34 维 SO3 → 编码视频。

官方转换器写出的是 **34 维**（见[附录](#附录34-维-so3-动作空间布局)）：`torso9 + left_arm9 + left_gripper1 + right_arm9 + right_gripper1 + head2 + chassis3`。其中位姿段由 `xyz_quat_to_so3` 把 7 维（xyz+四元数）转 9 维 SO3；head 取关节最后 2 维，chassis 取关节前 3 维。

> ⚠️ **但训练只用前 31 维，底盘不参与学习。** `pi05/utils/base_processor.py::_get_default_action_config()` 里 `state_source_config` / `action_source_config` / `target_config` 三者都只定义到 31 维（torso→head），**不含 chassis**；34 维的 `output_config` 只在推理输出端出现，多出的 `chassis:(31,34)` 由 `output_extract_transform` 从当前 state 原样复制。所以**模型不预测底盘**——即使喂 34 维真机数据，末 3 维在训练时也被丢弃。想让模型自己协调底盘，必须改框架（把 chassis 加进 action/target config）。
>
> 推论：自写转换器产出 **31 维**是正确且足够的（本仓库 `convert/hdf5_to_pi05.py` 就是 31 维，v1/v2 都这样训）。但**评测客户端仍必须发 34 维 state**，否则 `output_extract_transform` 会报 `State dimension 31 does not match output_config dimension 34`——两端约定不同，不是矛盾。

产出目录结构：`<out>/<dataset_name>/lerobot_so3_data_30hz/`，含 `meta/`（info.json / episodes.jsonl / tasks.jsonl）、`data/`（parquet）、`videos/`（mp4）。

## 7. 计算归一化统计

训练前必需。归一化路径按**配置文件名**派生，`compute_norm_stats` 与 `train` 必须用**同名配置**。

```bash
export HF_HUB_OFFLINE=1
bash scripts/train/compute_norm_stats.sh -c configs/train_example/<你的配置>.yaml
```

生成 `<normalization_base_path>/<配置名>/.../norm_stats.json`。建议 `normalization_base_path` 用**绝对路径**，避免 compute 与 train 工作目录不同导致找不到（见 [第 11 节](#11-已知坑与解法)）。

## 8. 训练

### 8.1 配置要点

```yaml
model_name_or_path: "<解压后的 pi05_base_bfloat16 目录>"
attn_implementation: "flash_attention_2"    # 没装 flash-attn 改 "eager"
torch_dtype: "bfloat16"

model_kwargs:
  chunk_size: 32
  freeze_vision_encoder: true      # 小数据集冻结防过拟合
  train_expert_only: true          # 只训动作 expert；显存紧张必开
  GPU_memory_opt_level: 1          # 显存不足设 2（gradient checkpointing）

processor_kwargs:
  normalization_mode: {state: "quantile", actions: "quantile"}
  normalization_base_path: "<绝对路径>/norm"

robot_datasets:
  - repo_id_list: [["lerobot_so3_data_30hz", 0.9]]   # 90%训/10%验
    dataset_root: "<数据集上级目录>"

deepspeed: "configs/deepspeed/zero2.json"     # 多卡；单卡可注释
max_steps: 30000
save_steps: 2000                              # 多留 checkpoint 便于挑选
save_total_limit: 8
```

### 8.2 显存与多卡

| 硬件 | 策略 |
|---|---|
| 单卡 80G（A100/H100） | 全参微调可行 |
| 多卡 4090/3090（24G×N） | ZeRO-2 分片，`train_expert_only=true`，per-device batch 2，梯度累积凑有效 batch |
| 单卡 24G | 极限：冻主干 + opt_level 2 + batch 1 + flash-attn，仍可能 OOM |

flash-attn 是省显存关键；24G 上没有它基本 OOM。

### 8.3 启动

```bash
export HF_HUB_OFFLINE=1
nvidia-smi                             # 挑空闲卡
export CUDA_VISIBLE_DEVICES=0,1,2,3    # -n 卡数须与此一致

# 先小步验证（200 步不 OOM、loss 下降）——注意 max_steps 要写进配置，命令行覆盖无效
bash scripts/train/train.sh -c configs/train_example/<配置>.yaml -n 4

# 正式训练挂后台
nohup bash scripts/train/train.sh -c configs/train_example/<配置>.yaml -n 4 > train.log 2>&1 &
```

checkpoint 落在 `<output_dir>/<配置名>/checkpoint-*/`。**小数据集勿训过头**——loss 很快降到很低是过拟合信号，用中间 checkpoint（评测挑最优），不要默认取最后一步。

## 9. 推理服务

```bash
export HF_HUB_OFFLINE=1; export CUDA_VISIBLE_DEVICES=0
# infer 配置：checkpoint 指向某个 checkpoint-XXXXX 的绝对路径；server_type: "sync"
bash scripts/infer/infer.sh -c configs/infer_example/<配置>.yaml
```

监听 `ws://0.0.0.0:8000`。**评测用 `server_type: "sync"`**（单客户端顺序推理，协议简单）；`async` 是为真机高频部署的 RTC 双流架构，评测客户端要另写。

## 10. 闭环评测

推理服务起好后，评测客户端组装观测发过去、收 action chunk 执行。观测协议（msgpack + WebSocket）：

- `cartesian_so3_dict.cartesian_pose_state`：**34 维**（含 chassis）
- `images_dict.head.rgb` / `left_wrist.rgb` / `right_wrist.rgb`：**CHW float[0,1]**（与训练 LeRobot 输出一致，不是 HWC uint8）
- `prompt`：任务字符串

**真机评测**用官方 `astribot_eval`（自带 250Hz 执行 + WBC/IK + 安全层）。仿真评测需自写客户端把模型输出的 SO3 动作经 IK 转关节下发（参考本仓库 `eval/pi05_eval_client.py`）。真机部署务必：动作限幅、异常自动急停、人在急停按钮旁。

## 11. 已知坑与解法

微调链路实测踩过并解决的坑，按环节归类：

**环境 / 网络**
- tokenizer 下载超时 → 魔搭下载 + 指向本地 + `HF_HUB_OFFLINE=1`。
- 视频编码 `No such file: ffmpeg` → conda 装 ffmpeg。
- **装了 ffmpeg 仍报 `FileNotFoundError: 'ffmpeg'`** → 后台起任务时用绝对路径调 `python`（如 `nohup /path/envs/xxx/bin/python -u convert.py &`）会**绕过 conda 激活**，ffmpeg 不在 `PATH` 上。显式加：`export PATH=<env>/bin:$PATH`。转换会在第一条 episode 编码视频时才崩，前面的 parquet 已写出，看着像跑起来了。
- **官方脚本报 `Error: could not locate a conda installation`** → `scripts/common/conda.sh` 只在 `$HOME/miniconda3`、`$HOME/anaconda3`、`/opt/conda`、`/usr/local/{miniconda3,anaconda3}` 这几个**硬编码路径**里找 conda。conda 装在别处（本项目是 `/data0/miniconda3`）时，它靠 `command -v conda` 兜底——交互式登录有 PATH 所以没事，**但 `nohup`/`setsid`/cron 等非交互后台任务没加载 profile，两条路同时断掉，脚本秒退**。修法：起任务前 `export PATH=/data0/miniconda3/bin:$PATH`（只要 `conda` 可见，脚本自己会 `conda info --base` 定位并 source `profile.d/conda.sh`）。凡是 `scripts/train/*.sh`、`scripts/infer/*.sh` 都走这个函数，后台跑都要加。
- **容器内以 root 写出的数据目录，宿主机普通用户改不动**（`mv`/`rm` 都会 Permission denied）。要筛选/重组数据就在别处建**符号链接目录**再喂给转换器，比申请 sudo 省事。

**转换（自采/自写转换时）**
- `add_frame() missing 'tasks' and 'coarse_task'` → 官方 fork 的 lerobot 签名是 `add_frame(frame, tasks:list, coarse_task:str)`。
- `save_episode` 空 buffer（np.stack empty）→ fork 新增 `sub_task_index`(shape 2) 特征，`add_frame` 不自动填，需在 frame 里补 `[t, T-1-t]`（单任务即整条 episode）。
- `create()` 报目录已存在 → 每次重跑先删输出目录（`exist_ok=False`）。
- `consolidate` 崩在 `load_images` 属性 → `create()` 构建的 dataset 缺该属性；用 `consolidate(run_compute_stats=False)`（pi05 有自己的 norm，不需要 lerobot 内置 stats）。

**训练**
- 归一化路径找不到 → compute 与 train 工作目录不同导致相对路径错位；`normalization_base_path` 用绝对路径，且两步用同名配置。
- `lm_head.weight newly initialized` 警告 → 正常，base 权重不含语言模型头，微调会训它。
- 命令行 `--max_steps` 不生效 → 该版本 main.py 不接受覆盖参数，改写进配置文件。

**评测**
- 视觉编码器 `expected 3 channels, got 224` → 图像要发 **CHW** 不是 HWC。
- `State dimension 31 does not match output_config dimension`（34）→ state 要发 **34 维**（末尾补 chassis 3 维）。
- 客户端连上但不动 → `server_type` 是 async；评测改 sync。
- ROS 侧客户端卡 `wait_ready` → 终端没 `source env.sh`（ROS_DOMAIN_ID 不对）。
- **⚠️ 评测必须 `rtc_delay: 0`，否则成功率会假性归零（最坑的一个）。**
  `serving/policy.py` 里 `cls = RtcPolicy if rtc_delay > 0 else Policy`——只要 `rtc_delay > 0`
  就走**有状态**的 `RtcPolicy`：它把上一次推理的 `self._last_absolute_actions` 当作动作前缀
  条件下一次推理，而前缀的偏移量 `execute_steps` 由 `obs["obs_timestamp"]` 反推。
  自写评测客户端通常**不发** `obs_timestamp`，于是前缀用错步长、跨请求不断累积漂移。
  - **实测量级**：同一份训练帧回放，`rtc_delay=3` 且复用连接时预测中位误差 **34.4cm**；
    改成 `0`（或每帧重连）后 **0.35cm**。闭环评测因此从"成功率 0%、动作看似收敛到某个
    固定点"变成正常——**这个现象极易被误诊为"因果混淆/模型没学会"**，本项目就误判过一轮。
  - RTC 是给真机高频部署用的（那边由执行系统正确提供时间戳），评测别开。
- **一条连接 = 一条 episode**。`websocket_policy_synchronous.py` 的 `_handler` 在新连接时
  调 `self._policy.reset()` 清策略状态，官方注释写明 "New connection = new episode"。
  评测客户端若复用一条连接跑多个 episode，第 2 条起会被上一条的残留状态污染——**每条
  episode 重连一次**。
- **诊断方法（值得常备）**：成功率为 0 时，"模型没学会"和"评测管线接错"从成功率上分不开。
  用 `eval/replay_check.py` 拿**训练集自己的帧**按评测协议回放，与 parquet 里的真值动作比对：
  误差亚厘米 → 模型没问题，去查评测侧；误差大于"原地不动"基线 → 才是模型/数据问题。
  它还带 `--fresh-conn`，用来区分"预测不准"和"被跨请求状态污染"。

**框架语义（不看源码容易判断错）**
- **`model_kwargs` 是"覆盖"而非"完整指定"**。`trainer/config.py` 的 `to_config_kwargs()` 把它 `update` 进去，再传给 `train.py` 里的 `AutoConfig.from_pretrained(path, **kwargs)`。所以：**列出的键覆盖 checkpoint 自带 `config.json`，没列出的键静默继承**。从别人的 checkpoint 续训时尤其要小心——比如官方 `pi05_pnp` 的 config 里 `train_expert_only=false`、`freeze_vision_encoder=false`、`training_time_rtc=true`、`GPU_memory_opt_level=0`，不显式覆盖就会全参微调 + 开 RTC，24G 卡直接 OOM。**建议把在意的键全部显式写出**。
- **processor 不从 checkpoint 目录加载**。`train.py::_build_processor` 里 `AutoProcessor.from_pretrained` 分支是**注释掉的**，实际走 `create_processor(model_type, **processor_kwargs)`，即完全由 YAML 的 `processor_kwargs` 构建。两个后果：(1) 别人 checkpoint 里附带的 `norm_stats` **不会**被误用，你的 `normalization_base_path` 说了算（好事）；(2) 它附带的 tokenizer 也**不会**被使用，离线 tokenizer 补丁仍然必须。
- **图像增强默认就是开着的**。`processor_pi05.py` / `base_processor.py` 里 `image_transforms is None` 时的默认值就是 `default_224_head_aug` / `default_224_wrist_aug`，`train.py` 也注释说 "will use defaults from processor"。所以不写这一项 ≠ 没有增强。head 的增强链是 `resize_with_pad → random_resized_crop(scale 0.95) → rotation ±5° → color_jitter(亮度0.7~1.3/对比0.6~1.4/饱和0.5~1.5) → rescale[-1,1]`，wrist 少了 crop 与 rotation。
- **`remove_image_padding` 作用在图像 token 上，不是像素**。`modeling_pi05.py` 里 `img_emb = img_emb[:, start:end]`，默认 `[48, 208]` 表示从 256 个 image token 里取中间 160 个，用于剔除 `resize_with_pad` 造成的黑边 token。框架默认值即如此，不是某个 checkpoint 特有。
- **`normalization_mode` 换模式不需要重算 norm**。`norm_stats.json` 里 `mean / std / q01 / q99 / min / max` 一次性全存，模式只决定用哪几个字段。但**换配置文件名就要换 norm 目录**（路径按配置名派生），同一数据集可以直接 `cp -r` 过去。
- **`training_time_rtc` 不需要数据里有额外字段**。它只是在 `modeling_pi05.py` 里对 flow-matching 的 time 加掩码（随机采 delay ∈ [0, rtc_max_delay]，把前 delay 个时间步的 time 置 0，模拟"已提交的动作前缀"），显存开销可忽略。
- **官方 checkpoint 可以直接当微调起点**。`pi05_pnp/checkpoint-100000` 与 `pi05_base_bfloat16` 的张量名完全一致（812 个），只多 `paligemma_with_expert.paligemma.lm_head.weight`（bf16 下 257152×2048 = 1.05G，正好解释两者体积差）。这也印证了"`lm_head.weight newly initialized` 警告正常"——裸底座确实不含语言模型头。

**方法层面（最重要）**

- **⚠️ 先确认"要学的东西在观测里"，再谈任何训练方法——本项目为此白跑了三轮训练。**

  现象是典型的"因果混淆"：模型忽略视觉，对所有物体位置输出同一个动作。但**真因不是分布太窄、
  数据太少或过拟合**，而是**观测里根本没有物体位置的信息**：

  采集时头部相机在跟踪目标物，于是 `物体的像素位置 = f(物体世界位置, 头部朝向)`。而头部朝向
  一度既没被记进 hdf5（`state_layout` 只有 `torso4+arm7+grip1`），转换时又被 `--head` 默认值
  写死成 `[0,0]`。两条路同时断掉，模型无法反解物体在世界何处。

  量化（`eval/head_info_check.py`，300 条留一法交叉验证，反解物体位置的 RMSE）：

  | 输入 | RMSE |
  |---|---|
  | 常数基线（永远猜平均值） | 16.39 cm |
  | **只用像素位置** | **16.23 cm ← 与基线持平，信息量为零** |
  | 只用头部角度 | 2.03 cm |
  | 像素 + 头部 + 二次/交叉项 | **1.63 cm** |

  在这种情况下，加数据、拉宽分布、换更强的起点、调步数与学习率**全部无效**。

  **修法**：采集时记录真实 head 关节角（`state` 由 12 维变 14 维），转换时写进 `state[29:31]`。
  或者退一步，采集时用 `--no-head-track` 让头部固定，使像素位置直接对应世界位置。

- **警惕"专家用了模型看不到的信息"。** 脚本专家直接读 TF 真值 `node.object_pos(name)`，
  所以演示数据完美无缺；但模型只有图像 + state。这种信息不对称，表现出来和过拟合、
  因果混淆一模一样，会把排查方向完全带偏。**写专家时就该逐项自问：它用到的每个量，
  模型能从观测里拿到吗？** 拿不到的，要么记进观测，要么别让专家依赖它。

- **成功率为 0 时，先分离"模型"与"管线"。** 二者从成功率上完全分不开，而管线故障往往
  不止一个（本项目同时存在 4 个，每个都能单独造成 0%）。推荐顺序：
  1. `eval/head_info_check.py` —— 观测里有没有要学的信息？没有就别往下查了
  2. `eval/replay_check.py` —— 拿训练帧回放，亚厘米误差说明模型没问题，去查评测侧
  3. `eval/obs_probe.py` —— 评测端观测与训练分布是否一致（像素统计 + 存图肉眼比对）
  4. `eval/openloop_replay.py` —— 开环重放专家动作，隔离 IK/下发/时序
  5. 都过了才去动训练配方

- **诊断指标本身也会骗人，这三个教训值得记住**：
  - **用抗离群统计量**。用标准差判断"模型输出是否随物体位置变化"时被少数离群点骗过：
    std 显示 10~14cm（像在响应），换成 MAD 只有 1.5~3.6cm（其实近乎恒定），20 条里 11 条
    落在同一点 5cm 内。`np.corrcoef` 同样对离群点敏感。
  - **别把"每条 episode 的首个动作"当判据**。所有 episode 都从同一初始姿态起步，
    训练数据里首个动作**本来就是同一个值**，它恒定是正确行为，不是因果混淆。
  - **`replay_check.py` 通过 ≠ 模型会用视觉**。该任务里动作与当前状态只差约 1.8cm，
    一个只会"复制当前状态"的模型也能拿到低误差（脚本里已用"原地不动基线"对照，但仍需注意）。

- **原来那条结论保留备查（已被上面推翻）**：~~因果混淆的根因是数据分布太窄 + 初始姿态固定 +
  过拟合，解法是加大随机化范围、增加数据量、选中间 checkpoint~~。分布随机化本身仍然是必要的
  好习惯（官方 pnp 数据就有三档桌高、夜间光照等），但它**不是**本项目 0% 成功率的原因。

## 附录：34 维 SO3 动作空间布局

`cartesian_so3_dict.cartesian_pose_state` / `cartesian_pose_command` 布局（官方固定）：

| 段 | 索引 | 维度 | 内容 |
|---|---|---|---|
| torso | 0:9 | 9 | SO3 位姿（xyz + 旋转矩阵前两行 6D） |
| left_arm | 9:18 | 9 | SO3 位姿 |
| left_gripper | 18:19 | 1 | 标量 |
| right_arm | 19:28 | 9 | SO3 位姿 |
| right_gripper | 28:29 | 1 | 标量 |
| head | 29:31 | 2 | yaw / pitch 关节 |
| chassis | 31:34 | 3 | x / y / yaw |

SO3 编码：`matrix_to_so3(R) = R[:2, :].reshape(6)`（旋转矩阵前两行展平）；`xyz_quat_to_so3` 把 7 维位姿转 9 维。训练时 delta 与坐标系变换由 processor 内部处理，数据侧只存 base 系绝对位姿。
