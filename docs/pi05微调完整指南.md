## 0. 真机 vs 仿真：差异速查

从仿真链路转过来的人**最容易在这张表上翻车**——好几处约定是反的。

| 环节 | 仿真评测（旧） | **真机部署（本文）** | 依据 |
|---|---|---|---|
| 推理服务类型 | `server_type: "sync"` | **`server_type: "async"`** | `configs/infer_example/example_pi05.yaml` |
| RTC 延迟 | **必须 `rtc_delay: 0`** | **`rtc_delay: 3`（官方默认）** | 同上；真机由执行系统提供正确 `obs_timestamp` |
| 连接模式 | 一条连接 = 一条 episode，客户端自己重连 | sender/receiver 双角色，**新 sender 连接 = 新 episode 自动 reset** | `websocket_policy_asynchronous.py::_handle_sender` |
| 观测 state | 34 维（末 3 维补 chassis） | 34 维 | `astribot_control_base.py` `state_dim = 34` |
| state 语义 | 实测值 | **指令值（`get_desired_*`）** | `astribot_control_base.py::_set_obs_state` |
| 动作执行 | 自写客户端 IK + 关节下发 | **官方 250Hz WBC 执行 + 实时轨迹生成** | `astribot_vla_execute.py::control_loop` |
| 头部 | 采集时脚本跟踪目标物 | **`head_follow_flag` 跟随末端执行器** | `astribot_vla_execute.py:141` |
| 数据 HDF5 | 自采 12/14 维精简格式 | **官方 25 维关节 + 双 poses_dict 完整格式** | 附录 B |
| 转换器 | 自写 `convert/hdf5_to_pi05.py`（31 维） | **官方 `pi05.tools.convert_hdf5_to_lerobot`（34 维）** | — |
| sim2real 差距 | 有（纯仿真策略上真机基本失败） | **无** | — |

> **`rtc_delay` 那一行是最关键的反转。** 仿真侧因为自写客户端不发 `obs_timestamp`，开 RTC 会让预测误差从 0.31cm 炸到 34.4cm、成功率假性归零（详见 [§13](#13-已知坑与解法)）。真机不同：`astribot_send_obs.py` 每帧都带 `obs_timestamp`，RTC 的动作前缀能正确对齐，**这时 `rtc_delay: 3` 是对的**，它正是为真机高频部署设计的。**别把仿真那条"必须关 RTC"的结论照搬到真机。**

## 1. 总览与架构

pi0.5 = PaliGemma（视觉-语言）+ Gemma Expert（动作），动作空间为全身 34 维笛卡尔 SO3（**但训练只用前 31 维**，见 [§6.3](#64-34-维与-31-维底盘不参与学习)）。

### 1.1 数据到模型

```
真机遥操作采集 ──> 官方 HDF5（25维关节 + 双 poses_dict + 三相机 JPEG）
                        │
                  审查筛选（Foxglove）+ 标注（prompt / episode_success）
                        │
        convert_hdf5_to_lerobot ──> LeRobot 数据集（34 维 SO3 + mp4）
                        │
              compute_norm_stats ──> norm_stats.json
                        │
                   train.sh ──> checkpoint
```

### 1.2 真机闭环运行时

三个进程 + 一个远程 GPU 服务，通过共享内存与 WebSocket 串起来：

```
┌────────────── 机器人本体电脑（ROS + SDK） ──────────────┐
│                                                        │
│  主控制进程 (CPU -1)  astribot_vla_execute.py          │
│    • 250Hz 控制循环，消费实时轨迹                       │
│    • set_different_type_command(..., use_wbc=True)     │
│    • 写 state 共享内存（34 维，指令值）                 │
│         │                          ▲                   │
│         │ mp_traj_queue            │ shm: state        │
│         ▼                          │                   │
│  VLA 接收进程 (CPU -2)     观测发送进程 (CPU -3)        │
│  astribot_eval_base.py     astribot_send_obs.py        │
│    • role: receiver          • 订阅三路相机 topic       │
│    • 收 action chunk         • resize 224 + CHW float   │
│    • RTG 生成实时轨迹        • role: sender             │
│         ▲                          │                   │
│  （可选）VR 干预进程 (CPU -4)  astribot_human_intervene │
└─────────┼──────────────────────────┼───────────────────┘
          │        WebSocket :8000   │
          └──────────┬───────────────┘
                     ▼
         ┌────────────────────────────┐
         │  GPU 机：serve_policy       │
         │  server_type: async         │
         │  共享内存 + 主进程推理       │
         └────────────────────────────┘
```

**关键前提：数据是一切。** 模型能否学会取决于数据的**任务一致性**与**分布多样性**，以及——比这两条更前置——**要学的映射是否真的存在于观测里**（[§4.6](#46-观测信息量自检真机版必做)）。

### 1.3 部署拓扑选择

推理服务放哪，是延迟与显存的权衡：

| 方案 | 网络延迟 | 显存 | 适用 |
|---|---|---|---|
| **就近一台 x86 GPU 机（推荐）** | 有线千兆局域网单跳，约 1~3ms | 单卡 24G 足够（bf16 + flash-attn，权重 6.8G） | **默认选这个**，与机器人同一交换机 |
| 远端服务器（如远程训练机） | 取决于网络，十几到几十 ms | 充裕 | 仅在就近无卡时用，且必须实测延迟 |
| 本体电脑 / 边缘设备 | 最低（本机回环） | 权重 bf16 占 6.8G | ⚠️ 算力通常不够，上机前务必实测延迟 |

选定后在 `astribot_eval/config/config.py` 填 `vla_host` / `vla_port`。

#### 延迟预算

pi0.5 是 3B VLM + 10 步 flow-matching 去噪，**单次推理是一百到几百毫秒量级**（本项目在被训练争用的 4090D 上实测 17,867 次，中位 516ms、最快 248ms；独占的现代单卡可到 100~250ms）。**不是几十毫秒——按这个量级做规划。**

闭环能容忍的延迟有**两道硬上限**：

1. **`time_threshold`（默认 1.0s）**——超过它没收到新轨迹就报 `VLA超时` 并停下问 `(y/n)`
2. **RTC 的 `execute_steps` 钳位**——`policy.py::_calculate_execute_steps`：
   ```python
   execute_steps = max(1, round(time_diff / control_period))     # control_period = 1/30 s
   execute_steps = min(execute_steps, chunk_size - rtc_delay)    # = 32 - 3 = 29
   ```
   29 步 ÷ 30Hz ≈ **0.97s**。推理延迟一旦超过它，`execute_steps` 饱和在 29，**RTC 截取的动作前缀不再对应真实已执行进度**，跨 chunk 衔接失效。

所以**单次推理要稳定在 1s 以内**，留余量应控制在 **600ms 以内**。提速手段按性价比排序：**推理卡别和训练混跑**、`denoise_num_steps` 10 → 5（去噪部分近似线性）、`torch.compile`/TensorRT、换更快的卡。

**用有线，别用 WiFi**——抖动比均值更致命，`obs_timestamp` 的时间差直接进 RTC 的 `execute_steps` 计算。

## 2. 两套环境搭建

真机链路涉及**两套互不干扰的环境**，装在不同机器上，PyTorch 版本冲突问题天然消失。

### 2.1 GPU 机：训练与推理（`astribot_pi05`）

```bash
# Python 3.11 + CUDA 12.1+（推荐 12.4）
conda create -n astribot_pi05 python=3.11 -y && conda activate astribot_pi05
cd <astribot_pi05 仓库>/astribot_pi05
bash install.sh          # torch 2.7 + transformers 补丁 + flash-attn（尽量装上，省显存）
```

**境内网络两项必做：**

1. **tokenizer 离线化**。训练/推理要加载 `google/paligemma-3b-pt-224` 的 tokenizer，境内直连 HuggingFace 常超时。从魔搭下载：

   ```bash
   pip install modelscope -i https://mirrors.aliyun.com/pypi/simple/
   python3 -c "from modelscope import snapshot_download; print(snapshot_download('AI-ModelScope/paligemma-3b-pt-224', allow_patterns=['tokenizer*','*.json','special_tokens*']))"
   export HF_HUB_OFFLINE=1      # 训练/推理都要
   ```

   > ⚠️ **不要把下载目录硬编码进 `processor_pi05.py`**。换机器/换账号就崩，且报错发生在 processor 构造阶段很难定位。应用本仓库补丁 `patches/0001-tokenizer-path-resolution.patch`，它把来源改成四级解析：`tokenizer_path` 参数 → 环境变量 `ASTRIBOT_TOKENIZER_PATH` → 本地常见位置 → 回退 hub id。之后换机器只需 `export ASTRIBOT_TOKENIZER_PATH=<含 tokenizer.model 的目录>`。
   > **补丁打在官方框架仓库上，重装框架后要重新 `git apply`。**
   >
   > 顺带一个事实：官方 `pi05_pnp` checkpoint 自带的 `processor/tokenizer.model` 与魔搭副本 md5 完全相同，可互换。

2. **ffmpeg**（视频编码，转换与训练都依赖）：

   ```bash
   conda install -n astribot_pi05 -c conda-forge ffmpeg -y
   ```

### 2.2 机器人本体电脑：执行系统（`astribot_eval`）

| 组件 | 要求 |
|---|---|
| Python | 3.8 – 3.12（加密 `.so` 按版本分发，见 `tools/diff_py_version_use/`） |
| ROS | ROS1 (Melodic/Noetic) 或 ROS2 (Humble)，由 `env.sh` 自动探测写入 `ROS_VERSION_VLA_USE` |
| SDK | 官方 Astribot SDK（本体电脑通常是 aarch64 + ROS2） |
| CPU | ≥ 8 核（进程要绑核 -1/-2/-3/-4） |
| 内存 | ≥ 8GB |

```bash
pip install cvxpy pynput websockets msgpack numpy opencv-python

# 顺序不能反：先 ROS，再 SDK，最后项目
source /opt/ros/<distro>/setup.bash
source <sdk>/env.sh
cd <astribot_pi05 仓库>/astribot_eval && source env.sh
```

**首次使用必跑基准测试**，它测定本机的轨迹生成与 sleep 补偿参数：

```bash
python3 tools/run_benchmark.py
# 把输出写回 config.py 的 traj_generate_cost_time / sleep_cost_time
```

> 这两个参数直接影响 250Hz 循环的节拍精度，**不要手抄别人机器的值**。

### 2.3 后台任务的 PATH 坑（GPU 机，反复踩）

conda 装在非标准位置（如 `/data0/miniconda3`）时：

- 用绝对路径调 `python` 绕过 conda 激活 → `ffmpeg` 不在 `PATH`，转换崩在 `FileNotFoundError: 'ffmpeg'`。
  修：`export PATH=<conda>/envs/astribot_pi05/bin:$PATH`
- 跑官方 `scripts/train/*.sh` / `scripts/infer/*.sh` → 它们调的 `scripts/common/conda.sh` 只认几个**硬编码路径**（`$HOME/miniconda3`、`$HOME/anaconda3`、`/opt/conda`、`/usr/local/{miniconda3,anaconda3}`），兜底靠 `command -v conda`。交互式登录有 PATH 所以没事，**但 `nohup`/`setsid`/cron 不加载 profile，两条路同时断掉，脚本秒退报 `could not locate a conda installation`**。
  修：`export PATH=<conda>/bin:$PATH`（**conda 根的 bin，不是 env 的 bin**）

## 3. 安全规程（真机第一优先）

**这一节不是形式主义。** 模型输出的是全身 34 维位姿指令，经 WBC 以 250Hz 执行，出错时机器人会以正常速度运动到错误位置。

### 3.1 每次开机前

- [ ] 机器人周围清场，工作空间内无人、无易碎物
- [ ] **急停按钮在手边且可达**，操作者不离岗
- [ ] 确认 `config.py` 的 `start_joints_pose` 是安全姿态，且**远离关节限位**
- [ ] `speed_rate` 从 **0.5** 起步，确认行为正常后再升到 1.0（范围 `[0.0, 1.5]`）
- [ ] 桌面/夹爪上没有上一轮遗留的物体

### 3.2 首次接入新模型时

新 checkpoint 第一次上机，**先做无风险的链路验证**：

1. 起推理服务，确认能收到观测——服务端每次推理会打印 `Inference time: XX ms`
2. 本体侧先只跑观测发送进程，确认打印 `Img / state data received.`
3. 确认无误后再起主控制进程，且 `speed_rate=0.5`
4. **人手放在急停上看完第一条 episode**

> 官方系统没有内置 dry-run 开关。若想更保守，可临时把 `speed_rate` 设到 0.1 观察轨迹方向是否合理。仿真侧的 `eval/eval_client_real.py` 提供了 `--dry-run` 与 `--max-delta` 限幅的实现思路，但它走的是 ACT 的 `serve_policy` 协议（端口 9000），**不能直接用于 pi0.5 真机链路**。

### 3.3 异常与停止

| 情况 | 系统行为 | 你要做的 |
|---|---|---|
| 超过 `time_threshold`（默认 1.0s）没收到新轨迹 | 打印 `VLA超时`，**在终端问 `是否继续？(y/n)`** | 前台运行才能回答；查网络与推理服务 |
| 收到空 action chunk | 置 `stop_flag`，主循环退出 | 查模型输出，多半是 checkpoint 或协议不匹配 |
| 正常停止 | — | `./stop.sh`（会清共享内存） |
| 异常退出后残留共享内存 | 下次启动 `create=True` 会失败 | `python3 script/base/clean_shm.py` |

> **`run.sh` 后台模式下超时会卡在 `input()` 上读不到输入。** 调试期一律用前台：`./run.sh -f`。

## 4. 数据采集（真机遥操作）

### 4.1 任务设计原则

- **单批一个任务**。一批数据对应一个明确任务。多任务分批采，或用逐段标注（[§5.3](#53-模式-b逐段标注多任务--子任务)）。
- **充分随机化**。每条 episode 换物体位置、初始条件、光照。分布越窄，模型越容易忽略视觉去背平均动作。
- **数据量**。单任务微调建议 ≥ 50 条成功演示，100+ 更稳。官方 pnp 数据集量级远大于此，且带三档桌高、夜间光照等变化。
- **一致性铁律**：采集时的**相机配置、初始位姿、控制频率、head 跟随策略、prompt 文本**，必须与部署时一致。任何一项不同都会造成观测分布偏移，而这种偏移在成功率上表现为"模型没学会"。

> 任务未定时，用这套占位模板起步：`<动作> the <物体> and place it into the <容器>`，全批统一一句，`--coarse-prompt` 直接传。**prompt 文本要一字不差地同步到 `config.py` 的 `prompt_list`**——训练和推理用的是同一个字符串，差一个标点都算不同 token 序列。

### 4.2 采集执行

用官方采集工具（VR / 遥操作）完成任务，每条录一个原始 HDF5。产出目录形如：

```
hdf5_output_<任务名>/
├── <任务名>_episode_0.hdf5
├── <任务名>_episode_1.hdf5
├── ...
└── task_info.json          # 采集会话元信息
```

`task_info.json` 实测内容：

```json
{
  "Name": "111",
  "Description": "zhauqu",
  "Operator": "1",
  "Count": "1/5",
  "Disk": "0.8/1876.7GB",
  "save_state": "waiting",
  "save_count": 0,
  "next_episode_index": 1,
  "failed_episodes": []
}
```

> `failed_episodes` 是采集端自己记的失败列表，**与转换器读的 `episode_success` attr 是两套机制**，别混。转换器不看 `task_info.json`（见 [§5.4](#54-成功标签)）。

### 4.3 采集频率与相机

- 数据频率 30Hz（转换时 `--fps 30`，且 `config.py` 的 `train_freq` 必须同为 `30.0`）
- 三路相机固定为 `head_rgbd` / `left_wrist_rgbd` / `right_wrist_rgbd`——**执行系统里这三个是写死的**（`astribot_vla_execute.py::start_camera` 与 `astribot_send_obs.py`），采集时也必须三路齐全
- 采集前确认相机 topic 正常发布：
  ```bash
  ros2 topic hz /astribot_camera/head_rgbd/color_compress/compressed
  ```

### 4.4 原始 HDF5 格式

完整实测结构见[附录 B](#附录-b真机-hdf5-实测结构)。转换器实际用到的部分：

| 组 / 键 | 形状 | 含义 |
|---|---|---|
| `poses_dict/astribot_{torso,arm_left,arm_right}` | (T,7) | **实际**笛卡尔位姿（xyz + 四元数） |
| `poses_dict/astribot_gripper_{left,right}` | (T,1) | 夹爪实际值 |
| `command_poses_dict/astribot_*` | (T,7)/(T,1) | 对应的**指令**位姿 |
| `joints_dict/joints_position_state` | (T,25) | 关节实际位置 |
| `joints_dict/joints_position_command` | (T,25) | 关节指令位置 |
| `images_dict/{head,left,right}/rgb` | (N,) | 拼接 JPEG 字节流 |
| `images_dict/{head,left,right}/rgb_size` | (T,) | 每帧 JPEG 字节数 |
| attrs `episode_success` | - | 成功标签（缺省视为成功） |

**25 维关节布局**（转换器 `_extract_cartesian_pose` 只取首尾）：

```
[0:3]   chassis  x / y / yaw          ← 转换器取 [:3]
[3:7]   torso    4 DOF
[7:14]  arm_left  7 DOF
[14:15] gripper_left
[15:22] arm_right 7 DOF
[22:23] gripper_right
[23:25] head      yaw / pitch          ← 转换器取 [-2:]
```

### 4.5 head 跟随：真机天然不缺信息，但别配错

真机执行时 `head_follow_flag: True`，头部跟随**末端执行器**（`astribot_vla_execute.py:141` 的 `set_head_follow_effector`）。这带来两个必须理解的点：

1. **头部角度确实被记录**。它在 `joints_dict` 的最后两维，转换器 `convert_hdf5_to_lerobot.py:811` 明确取 `[-2:]` 写进 `state[29:31]` 与 `command[29:31]`。**仿真侧那个"head 被写死成 `[0,0]` 导致三轮训练全废"的坑，在官方真机链路上天然不存在。**
2. **但头跟的是手，不是目标物**。所以 `head` 两维编码的是"手在哪"，不是"物体在哪"。物体位置只能来自图像；而相机在动，像素位置要还原成世界位置**必须联合 head 角度**。好在这对信息（像素 + head）都在观测里，映射是可解的——这正是仿真侧 v4 修复后的状态。

> ⚠️ **采集与部署的 head 策略必须一致。** 若采集时头部由 VR 操作者自由转动、部署时却是 `head_follow_flag=True` 跟随末端，两者的 `state[29:31]` 分布完全不同，图像视角也不同——模型会拿到训练时没见过的观测组合。**决定一种策略，两端都用它。**

### 4.6 观测信息量自检（真机版，必做）

这是仿真侧用三轮失败训练（v1/v2/v3 闭环成功率全 0%）换来的纪律，**真机同样适用**：

> **先确认"要学的东西在观测里"，再谈任何训练方法。**

采完首批数据、开训之前，做一次留一法回归自检：**能否从单帧观测反解出目标物的世界位置？**

- 输入：三相机图像里目标物的像素位置（人工标或检测器出）+ `state[29:31]` head 角度 + 二次/交叉项
- 输出：目标物世界坐标（可用"第一次抓到物体那一帧的末端位姿"近似）
- 对照：**常数基线**（永远猜训练集平均值）

判读标准：

| 结果 | 含义 | 行动 |
|---|---|---|
| RMSE ≈ 常数基线 | **观测里没有物体位置信息，怎么训都学不会** | 停下，改观测设计（换相机策略/加相机/固定头部） |
| RMSE 明显低于基线，且进入 1~2cm | 信息充足 | 可以开训 |
| 介于两者之间 | 信息不足以支撑精细抓取 | 先补信息，别急着调参 |

仿真侧的实测数字（`eval/head_info_check.py`，300 条留一法交叉验证）作为量级参考：

| 输入 | 反解 RMSE |
|---|---|
| 常数基线 | 16.39 cm |
| 只用像素位置（head 被清零时） | **16.23 cm ← 与基线持平，信息量为零** |
| 只用头部角度 | 2.03 cm |
| 像素 + 头部 + 二次/交叉项 | **1.63 cm** |

> **警惕"专家用了模型看不到的信息"。** 仿真里脚本专家直读 TF 真值，演示完美但模型只有图像 + state，这种信息不对称表现得和过拟合、因果混淆一模一样，会把排查方向完全带偏。真机遥操作里对应的问题是：**人类操作者用了模型拿不到的视角或信息**（侧头看、凭手感、听声音），而三路相机没拍到。采集前自问一句：**操作者做决策用的每条信息，模型能从这三路相机 + state 里拿到吗？**

对模仿学习，"标注是否完成"本质上就是**筛选出成功演示**——留下的即成功集。

### 5.1 转 MCAP 用 Foxglove 逐条看

```bash
pip install mcap h5py numpy opencv-python
python convert/official_hdf5_to_mcap.py --src <raw_dir> --out ./mcap
# Foxglove 打开 .mcap：/camera/head|left|right 看画面，/joints/state 画关节曲线
```

审查要点：抓空、滑落、碰翻、操作者中途修正过大、相机花屏或掉帧——这些都删掉或标失败。

### 5.2 模式 A：整批一个任务（推荐，零标注量）

单任务重复采集用这个——`--coarse-prompt` 给一句话，对所有帧写同一 prompt，不需要任何标注文件：

```bash
python3 -m pi05.tools.convert_hdf5_to_lerobot \
  --raw-path <raw_dir> --output-path <out> --dataset-name <任务名> \
  --coarse-prompt "<你的任务指令>" \
  --fps 30 --robot-type S1-stationary
```

### 5.3 模式 B：逐段标注（多任务 / 子任务）

不给 `--coarse-prompt`，转换器会去 `raw_path/Labels/` 找 JSON 标注（Label-Studio 风格：`videoFrameTool` 打关键帧 + `textTool` 写整段 coarse prompt）。每个关键帧标 `Arm`/`Object`/`Action` 三属性，转换器用内置 `ACTION_DICT`（`grab→"pick up the {}"`、`place→"place the {}"` 等）自动拼 fine prompt。适合长程 / 多子任务演示。

### 5.4 成功标签

成功标签不在 JSON，而在 HDF5 attr **`episode_success`**（转换器 `get_episode_success_flag` 读它：>0 记成功，**缺省默认 1**）。两种做法：

- **筛选式（简单）**：只留成功演示，不设 attr，失败的直接删源文件
- **显式标注**：审查后给每条写 attr

  ```python
  import h5py
  with h5py.File(path, "r+") as f:
      f.attrs["episode_success"] = 1   # 或 0
  ```

> **实测提醒**：官方样例 `111_episode_0.hdf5` **根本没有任何 attrs**，所以走的是"默认成功"这条路。别指望采集工具帮你写这个标签，**自己确认**。

## 6. 转换为 LeRobot 格式

### 6.1 命令

用官方转换器（[§5.2](#52-模式-a整批一个任务推荐零标注量) 的命令）。它做三件事：写 prompt 到 HDF5 → 逐帧组装 34 维 SO3 → 编码视频。

产出目录：`<out>/<dataset_name>/lerobot_so3_data_30hz/`，含 `meta/`（info.json / episodes.jsonl / tasks.jsonl）、`data/`（parquet）、`videos/`（mp4）。

### 6.2 state / action 怎么组装的

`convert_hdf5_to_lerobot.py::_extract_cartesian_pose`（`:801-813`）：

| 输出段 | `is_command=True`（action） | `is_command=False`（state） |
|---|---|---|
| torso / arm_left / arm_right | `command_poses_dict/*` → `xyz_quat_to_so3` | `poses_dict/*` → `xyz_quat_to_so3` |
| gripper_left / right | `command_poses_dict/astribot_gripper_*` | `poses_dict/astribot_gripper_*` |
| head (2) | `joints_position_command[-2:]` | `joints_position_state[-2:]` |
| chassis (3) | `joints_position_command[:3]` | `joints_position_state[:3]` |

### 6.3 训练与推理的 state 语义对齐（`--replace-state-with-action`）

**这是真机链路最容易被忽略、后果又最大的一个选择。**

- **默认（不加这个 flag）**：训练数据的 `state` 来自 `poses_dict` = **实测位姿**
- **推理时**：`astribot_control_base.py::_set_obs_state` 用的是 `get_desired_wbc_pose` / `get_desired_joints_position`，SDK 文档明确写着这是"**最近一次下发的位置指令**"，也就是**指令值**

两者语义不同。真机上指令与实测之间有跟随误差（贴桌操作、负载、接触时尤其明显），**训练看到的是实测、推理喂进去的是指令**，这就是一个静默的分布偏移。

转换器给了对齐开关：

```bash
--replace-state-with-action    # state 改用「上一帧的 command」（frame 0 除外）
```

它的实现（`convert_hdf5_to_lerobot.py:768-772`）正是 `_extract_cartesian_pose(file, frame_idx - 1, is_command=True)`——**与执行时"上一次下发的指令"精确对应**。

> **建议：真机训练加上 `--replace-state-with-action`。** 若不加，就要接受 train/infer 之间的 state 语义差，并在评测异常时把它列为头号嫌疑。
> **两种都试的话，务必换 `--dataset-name`**，否则两份数据混在一起分不清。

### 6.4 34 维与 31 维：底盘不参与学习

官方转换器写出的是 **34 维**（见[附录 A](#附录-a34-维-so3-动作空间布局)）：`torso9 + left_arm9 + left_gripper1 + right_arm9 + right_gripper1 + head2 + chassis3`。

> ⚠️ **但训练只用前 31 维。** `pi05/utils/base_processor.py::_get_default_action_config()` 里 `state_source_config` / `action_source_config` / `target_config` 三者都只定义到 31 维（torso→head），**不含 chassis**；34 维的 `output_config` 只在推理输出端出现，多出的 `chassis:(31,34)` 由 `output_extract_transform` 从当前 state 原样复制。
>
> **所以模型不预测底盘**——即使喂 34 维真机数据，末 3 维在训练时也被丢弃。想让模型自己协调底盘，必须改框架（把 chassis 加进 `action_source_config` 与 `target_config`）。
>
> 这一条推翻了一个很自然但错误的直觉："喂真机数据模型自然就会动底盘"。**不成立。**

### 6.5 图像处理

转换器把 JPEG 解码后 **BGR→RGB**（`frame[feature_key] = jpeg_frames[topic][frame_idx][..., ::-1]`）再编码进 mp4，分辨率保持原始；缩放到 224 由 processor 在训练时做（`resize_with_pad`）。

推理侧 `astribot_send_obs.py` 也做同样的两件事：`resize_with_aspect_ratio`（保持纵横比 + **黑边填充**）到 224×224，然后 BGR→RGB + HWC→CHW + `/255.0`。两端的 padding 策略一致，这是对的——**别去改成拉伸或中心裁剪**。

## 8. 训练

### 8.1 配置要点

```yaml
model_name_or_path: "<pi05_base_bfloat16 或 pi05_pnp/checkpoint-100000>"
attn_implementation: "flash_attention_2"    # 没装 flash-attn 改 "eager"
torch_dtype: "bfloat16"

model_kwargs:
  chunk_size: 32                   # 必须与 config.py 的 action_chunk_size 一致
  freeze_vision_encoder: true      # 小数据集冻结防过拟合
  train_expert_only: true          # 只训动作 expert；显存紧张必开
  GPU_memory_opt_level: 1          # 显存不足设 2（gradient checkpointing）
  training_time_rtc: true          # 真机要开 RTC，训练侧也开更匹配（见下）

processor_kwargs:
  normalization_mode: {state: "quantile", actions: "quantile"}
  normalization_base_path: "<绝对路径>/norm"

robot_datasets:
  - repo_id_list: [["lerobot_so3_data_30hz", 0.9]]   # 90%训/10%验
    dataset_root: "<数据集上级目录>"

deepspeed: "configs/deepspeed/zero2.json"     # 多卡；单卡可注释
max_steps: 30000
save_steps: 2000                              # 多留 checkpoint 便于挑选
save_total_limit: 8
```

> **`training_time_rtc` 与真机部署配套。** 它只是在 `modeling_pi05.py` 里对 flow-matching 的 time 加掩码（随机采 delay ∈ `[0, rtc_max_delay]`，把前 delay 个时间步的 time 置 0，模拟"已提交的动作前缀"），**不需要数据里有额外字段**，显存开销可忽略。既然真机推理开 `rtc_delay: 3`，训练时开它能让两端更匹配。

### 8.2 warm start 起点选择

| 起点 | 说明 |
|---|---|
| `pi05_base_bfloat16` | 裸底座。张量名与 pnp 完全一致（812 个），只少 `lm_head.weight` |
| `pi05_pnp/checkpoint-100000` | **官方已在 pick-and-place 上微调过**。任务同类时优先选它，收敛更快、成功率更高 |

> ⚠️ **从别人的 checkpoint 续训要小心 `model_kwargs` 的"覆盖"语义**：`trainer/config.py::to_config_kwargs()` 把它 `update` 进去再传给 `AutoConfig.from_pretrained(path, **kwargs)`，**列出的键覆盖 checkpoint 自带的 `config.json`，没列出的键静默继承**。官方 `pi05_pnp` 的 config 里 `train_expert_only=false`、`freeze_vision_encoder=false`、`GPU_memory_opt_level=0`，不显式覆盖就会变成全参微调，24G 卡直接 OOM。**把在意的键全部显式写出。**

### 8.3 显存与多卡

| 硬件 | 策略 |
|---|---|
| 单卡 80G（A100/H100） | 全参微调可行 |
| 多卡 4090/3090（24G×N） | ZeRO-2 分片，`train_expert_only=true`，per-device batch 2，梯度累积凑有效 batch |
| 单卡 24G | 极限：冻主干 + `GPU_memory_opt_level: 2` + batch 1 + flash-attn，仍可能 OOM |

flash-attn 是省显存关键；24G 上没有它基本 OOM。

**卡数变化时同步调 `gradient_accumulation_steps` 保持有效 batch 不变**，否则不同版本之间的对照不干净：

| 卡数 | `gradient_accumulation_steps` | 有效 batch |
|---|---|---|
| 4 | 4 | 32 |
| 3 | 5 | 30 |
| 2 | 8 | 32 |

### 8.4 启动

```bash
export HF_HUB_OFFLINE=1
nvidia-smi                             # 共享机器，先挑空闲卡
export CUDA_VISIBLE_DEVICES=0,1,2,3    # -n 卡数须与此一致

# 先小步验证（200 步不 OOM、loss 下降）——max_steps 要写进配置，命令行覆盖无效
bash scripts/train/train.sh -c configs/train_example/<配置>.yaml -n 4

# 正式训练挂后台
export PATH=<conda>/bin:$PATH          # 见 §2.3，否则秒退
nohup bash scripts/train/train.sh -c configs/train_example/<配置>.yaml -n 4 > train.log 2>&1 &
```

checkpoint 落在 `<output_dir>/<配置名>/checkpoint-*/`。

> **产物路径按配置文件名派生**——这既是坑也是工具：
> - norm → `<normalization_base_path>/<配置名>/...`
> - checkpoint → `<output_dir>/<配置名>/checkpoint-*`
>
> **换配置名 = 自动隔离产物**，两版可直接对照评测；反过来，**复用旧配置名会覆盖旧 checkpoint**。

**小数据集勿训过头**——loss 很快降到很低是过拟合信号。用中间 checkpoint（评测挑最优），不要默认取最后一步。**若最优 checkpoint 恰好是最后一个，说明还在变好，该训更久。**

## 9. 推理服务（真机版）

### 9.1 配置

```yaml
# configs/infer_example/<你的配置>.yaml
checkpoint: "<绝对路径>/outputs/pi05_.../<配置名>/checkpoint-XXXXX"
attn_implementation: "flash_attention_2"
torch_dtype: "bfloat16"

port: 8000
server_type: "async"          # ← 真机必须 async（sender/receiver 双角色）

policy_kwargs:
  warm_up_model: true         # 启动时预热，首次推理更快
  seed: 42

inference_kwargs:
  rtc_delay: 3                # ← 真机开 RTC；仿真自写客户端才要设 0
  denoise_num_steps: 10       # Flow Matching 去噪步数，降低可提速
```

### 9.2 启动

```bash
export HF_HUB_OFFLINE=1
export PATH=<conda>/bin:$PATH
export CUDA_VISIBLE_DEVICES=<一张空闲卡>
bash scripts/infer/infer.sh -c configs/infer_example/<你的配置>.yaml
```

监听 `ws://0.0.0.0:8000`。启动后日志出现 `WebSocket I/O worker started on 0.0.0.0:8000` 与 `Inference loop started in main process` 才算就绪。

> ⚠️ **检查 `scripts/infer/infer.sh` 有没有硬编码 `export CUDA_VISIBLE_DEVICES=0`。** 本项目在仿真阶段被这一行坑过——服务永远跑在 0 号卡上，无视外部设置。改成尊重外部值。

### 9.3 async 服务是怎么工作的

`websocket_policy_asynchronous.py`：

- **主进程跑推理**，一个子进程 `SubAndPubWorker` 负责 WebSocket I/O，两者通过共享内存交换数据
- **sender** 推观测进共享内存；**receiver** 收广播的 action
- **新 sender 连接 = 新 episode**：自动置 `reset_flag`，调 `policy.reset()` 清 RTC 残留前缀
- 广播循环每 1ms 轮询一次 `output_timestamp`，变了就把 `{"obs_timestamp", "actions"}` 发给所有 receiver

**固定尺寸的共享缓冲（改不了，必须对齐）**：

| 缓冲 | 尺寸 | 后果 |
|---|---|---|
| `head/left/right` | `(3, 224, 224)` float32 | 图像必须 **224×224 CHW float** |
| `state` | `(34,)` float64 | state 必须 **34 维** |
| `output_action` | `(32, 34)` float64 | **chunk 必须 32**，与模型 `chunk_size` 和 `config.action_chunk_size` 三方一致 |
| `prompt` | 128 字节 | prompt 超过 127 字节会被截断 |

## 10. 真机闭环执行 runbook

### 10.1 config.py 逐项

`astribot_eval/config/config.py`：

```python
vla_host: str = "<GPU 机 IP>"     # 推理服务地址
vla_port: int = 8000
time_threshold: float = 1.0       # 超时阈值(s)，超过没新轨迹就报警并询问

control_freq: float = 250.0       # 控制频率，建议 100-300
start_joints_pose: List = [...]   # 6 段 22 关节：torso4/armL7/gripL1/armR7/gripR1/head2

train_freq: float = 30.0          # 必须 = 训练数据频率
action_chunk_size: int = 32       # 必须 = 模型 chunk_size = 共享缓冲的 32

image_type: str = "float"         # ← 必须 "float"
image_resize_shape = {"head": (224,224), "left": (224,224), "right": (224,224)}

prompt_way: Optional[str] = "keyboard"   # ← 必须非 None，见下方警告
prompt_list: List[str] = ["<与训练完全一致的指令>"]

filter_flag: bool = False         # True 走 control_way="filter"，更平滑但有滞后
filter_para: float = 0.05         # 范围 [0.01, 0.2]
head_follow_flag: bool = True     # 与采集时一致
speed_rate: float = 1.0           # 首次上机用 0.5

traj_generate_cost_time: float = 0.0    # ← 跑 tools/run_benchmark.py 测定
sleep_cost_time: float = 0.0001         # ← 同上

human_intervene: bool = False     # True 会额外起 VR 干预进程
```

> ⚠️ **`prompt_way` 不能是 `None`。** 服务端 `BufferConfig.use_prompt` 默认 `True`，`_write_observation_to_buffers` 会取 `obs["prompt"]`；而 `astribot_send_obs.py` 只在 `prompt_way is not None` 时才往 obs 里塞 `prompt` 键。两者不匹配时服务端抛 `KeyError`，**被 `_handle_sender` 的 try/except 吃掉**，只在服务日志里留一行 warning，然后 5ms 重试——**表现为机器人一动不动、没有任何报错**。官方 README 写 `prompt_way` 默认 `None`，与 `config.py` 实际默认值 `"keyboard"` 冲突，**以 `config.py` 为准**。

> ⚠️ **`start_joints_pose` 以 `config.py` 实际值为准，别抄 README。** README 示例里那套是仿真用的 `[0.29,-0.58,0.29,0.0]`，与 `config.py` 里的实际默认值不同。**这个姿态必须与采集时每条 episode 的起始姿态一致**，否则模型开局就在分布外。

### 10.2 启动顺序

```bash
# ── GPU 机 ──
export HF_HUB_OFFLINE=1 PATH=<conda>/bin:$PATH CUDA_VISIBLE_DEVICES=<空闲卡>
bash scripts/infer/infer.sh -c configs/infer_example/<配置>.yaml
# 等到 "Inference loop started in main process"

# ── 机器人本体电脑 ──
source /opt/ros/<distro>/setup.bash
source <sdk>/env.sh
cd <repo>/astribot_eval && source env.sh

python3 script/base/clean_shm.py     # 清上次残留（stop.sh 也会做）
./run.sh -f                          # ← 调试期用前台，超时询问才能应答
# 或 ./run.sh -c config_pick         # 用 config/config_pick.py
```

`run.sh` 做的事：清共享内存 → 按 `human_intervene` 决定是否起 VR 干预进程（核 -4）→ 起主控制进程（核 -1，它内部再起 VLA 接收进程于核 -2）→ 起观测发送进程（核 -3）。

停止：

```bash
./stop.sh          # 优雅停止 + 清共享内存
```

### 10.3 一条 episode 的完整时序

1. 主控制进程 `move_joints_position(..., duration=5.0)` 回到 `start_joints_pose`
2. `_initialize_action()` 把当前指令位姿记为 `init_action`（收不到轨迹时就一直发它，即"原地保持"）
3. `set_head_follow_effector(head_follow_flag)`
4. 清空轨迹队列 → 起 VLA 接收子进程 → 置 `send_obs_flag = True`
5. 观测发送进程连服务并声明 `{"role":"sender"}`（**服务端据此 reset 策略状态 = 新 episode**），此后每收到一帧头部相机图像就发一次观测
6. 服务端推理 → 广播 → 接收进程收 `actions`，调 `RTG.traj_generator(...)` 生成实时轨迹对象，塞进 `mp_traj_queue`
7. 主控制进程 250Hz 循环：取轨迹 → `action.get_orin_value(current_time)` → SO3 转四元数 → `set_different_type_command(..., use_wbc=True)` → 写回 `state` 共享内存
8. 收到 `"Over"` 或超时或 `stop_flag` → 结束，回到第 1 步

> **观测发送节拍由头部相机回调驱动。** 只有 `color_callback_head_*` 会更新 `obs_timestamp` 并触发发送，左右腕相机只是更新各自的图像槽位。所以**头部相机掉帧 = 整个闭环停摆**，而左右腕掉帧只会让模型看到过期的腕部画面（更隐蔽）。上机前 `ros2 topic hz` 三路都要确认。

### 10.4 VR 人工干预（可选）

`human_intervene: True` 时额外起 `astribot_human_intervene.py`（核 -4），通过 `control_from_VLA` 共享标志在 VLA 与 VR 之间切换，`BlendTransitionMixin` 负责两者之间的平滑过渡。

用途：模型卡住时人接管救场，同时 `control_mode_labels` 会被记进数据（转换器读它写 `is_human_intervention` 特征），可用于后续的 DAgger 式迭代。

> 底盘在 VR 干预期间不受控——`_initialize_action` 把 episode 开始时的底盘值存进 `chassis_init`，干预全程持续下发该值。


接收：


### 11.3 RTC 是怎么用 `obs_timestamp` 的

`pi05/serving/policy.py::RtcPolicy`（`:289+`）：

```python
execute_steps = max(1, round((current_obs_timestamp - last_obs_timestamp) / control_period))
execute_steps = min(execute_steps, chunk_size - rtc_delay)
shifted_actions[:rtc_delay] = last_absolute_actions[execute_steps : execute_steps + rtc_delay]
```

即：**用两帧观测的时间差推算"上一个 chunk 已经执行了多少步"**，据此把上次预测的动作尾部截出来当本次推理的前缀条件，实现跨 chunk 的平滑衔接。

**这也解释了为什么仿真自写客户端不能开 RTC**：不发 `obs_timestamp` 时 `_calculate_execute_steps` 恒返回 1，前缀每次错位 `(execute_steps - 1)` 步并**跨请求累积**，预测越漂越远。真机的 `obs_timestamp` 是真实的相机接收时刻，所以是对的。

## 12. 判读与排障

### 12.1 排障顺序（照这个走能省很多时间）

成功率为 0 时，"模型没学会"和"链路接错"从成功率上**完全分不开**，而链路故障往往不止一个。按信息量从大到小查：

1. **观测里有没有要学的信息？** → [§4.6](#46-观测信息量自检真机版必做) 的留一法自检。**没有就别往下查，也别调参。**
2. **模型问题还是链路问题？** → 拿**训练集自己的帧**按 sender 协议回放，与 parquet 里的真值动作比对。误差亚厘米 → 模型没问题，去查链路侧。参考 `eval/replay_check.py` 的做法（它是 sync 协议写的，真机要改成 async 的 sender/receiver）。
3. **推理端观测与训练分布是否一致？** → 存图肉眼比对 + 像素统计。参考 `eval/obs_probe.py`。真机重点看：三路相机是否都活着、亮度/白平衡是否与采集时一致、resize 后有没有异常黑边。
4. **执行链路是否忠实？** → 把一条演示的 action 序列直接喂给执行系统开环重放，看机器人是否复现了当时的动作。参考 `eval/openloop_replay.py`。
5. 都过了，才去动训练配方。

### 12.2 诊断指标本身也会骗人

三条用血换来的教训：

- **用抗离群统计量。** 判断"模型输出是否随物体位置变化"时，标准差显示 10~14cm（像在响应），换成 MAD 只有 1.5~3.6cm（其实近乎恒定），20 条里 11 条落在同一点 5cm 内。`np.corrcoef` 同样对离群点敏感。
- **别把"每条 episode 的首个动作"当判据。** 所有 episode 都从同一 `start_joints_pose` 起步，训练数据里首个动作**本来就是同一个值**，它恒定是正确行为，不是因果混淆。
- **回放检查通过 ≠ 模型会用视觉。** 若动作与当前状态只差一两厘米，一个只会"复制当前状态"的模型也能拿到低误差。**务必带一条"原地不动"基线做对照。**

### 12.3 真机特有的观察点

| 现象 | 先查 |
|---|---|
| 机器人完全不动，服务端也没打印推理耗时 | `prompt_way` 是不是 `None`（[§10.1](#101-configpy-逐项)）；相机 topic 是否在发 |
| 服务端有推理日志，机器人不动 | receiver 是否连上；`mp_traj_queue` 是否有货；`speed_rate` 是不是 0 |
| 动作抖、有台阶感 | `traj_generate_cost_time` / `sleep_cost_time` 没跑 benchmark；网络抖动；试 `filter_flag: True` |
| 反复 `VLA超时` | 网络延迟 > `time_threshold`；推理太慢（降 `denoise_num_steps`）；WiFi 换有线 |
| 动作方向大致对但差几厘米 | state 语义没对齐（[§6.3](#63-训练与推理的-state-语义对齐--replace-state-with-action)）；训练步数不够 |
| 起手就往奇怪方向去 | `start_joints_pose` 与采集时不一致；prompt 文本与训练不一致 |

## 13. 已知坑与解法

### 13.1 环境 / 网络

- tokenizer 下载超时 → 魔搭下载 + 指向本地 + `HF_HUB_OFFLINE=1`（[§2.1](#21-gpu-机训练与推理astribot_pi05)）
- 视频编码 `No such file: ffmpeg` → conda 装 ffmpeg
- **装了 ffmpeg 仍报 `FileNotFoundError: 'ffmpeg'`** → 后台任务用绝对路径调 `python` 绕过了 conda 激活。显式 `export PATH=<env>/bin:$PATH`。**转换会在第一条 episode 编码视频时才崩，前面的 parquet 已写出，看着像跑起来了。**
- **官方脚本报 `Error: could not locate a conda installation`** → 见 [§2.3](#23-后台任务的-path-坑gpu-机反复踩)
- 本体电脑 `ModuleNotFoundError: No module named 'cvxpy'` → `pip install cvxpy pynput websockets msgpack`
- 共享内存残留导致启动失败 → `python3 script/base/clean_shm.py`

### 13.2 数据 / 转换

- **官方样例 HDF5 没有任何 attrs** → `episode_success` 缺省按成功处理，失败样本必须自己删或自己写 attr
- `add_frame() missing 'tasks' and 'coarse_task'`（自写转换器时）→ 官方 fork 的签名是 `add_frame(frame, tasks:list, coarse_task:str)`
- `save_episode` 空 buffer（`np.stack` empty）→ fork 新增 `sub_task_index`（shape 2）特征，`add_frame` 不自动填，需在 frame 里补 `[t, T-1-t]`
- `create()` 报目录已存在 → 每次重跑先删输出目录（`exist_ok=False`）
- `consolidate` 崩在 `load_images` 属性 → 用 `consolidate(run_compute_stats=False)`（pi05 有自己的 norm）
- **容器内以 root 写出的数据目录，宿主机普通用户改不动**（`mv`/`rm` 都 Permission denied）→ 要筛选/重组数据就在别处建**符号链接目录**再喂给转换器

### 13.3 训练

- 归一化路径找不到 → `normalization_base_path` 用绝对路径，且 compute 与 train 用同名配置
- `lm_head.weight newly initialized` 警告 → 正常，base 权重不含语言模型头，微调会训它
- 命令行 `--max_steps` 不生效 → 该版本 `main.py` 不接受覆盖参数，写进配置文件
- **复用旧配置名会覆盖旧 checkpoint 和 norm** → 换名字就是换产物目录，拿它做版本隔离

### 13.4 真机执行

- **⚠️ `prompt_way = None` 导致机器人静默不动**：服务端 `use_prompt=True` 取 `obs["prompt"]` 抛 `KeyError`，被 try/except 吞掉只留一行 warning。**这是最难查的一个，因为哪一端都不报错。**
- **`image_type` 必须 `"float"`**：服务端共享缓冲是 `(3,224,224) float32`，`"int"` 模式发的是 HWC uint8，`np.copyto` 会失败
- **`image_resize_shape` 不能设 `None` 或非 224**：同上，缓冲尺寸写死
- **`action_chunk_size` 必须 32**：`output_action` 缓冲是 `(32,34)`，与模型 `chunk_size` 三方一致
- **后台模式下超时询问读不到输入**：`./run.sh -f` 前台跑
- **头部相机掉帧 = 闭环停摆**：只有头部相机回调触发观测发送
- **`_receive_latest_message` 定义了但没被调用**（`astribot_eval_base.py`）：接收循环用的是 `receive_message()`，不丢弃积压消息。网络抖动时理论上会消费到过期的 chunk。若观察到"动作滞后于场景"，把接收改成调 `_receive_latest_message` 是第一个可试的修改。

### 13.5 框架语义（不看源码容易判断错）

- **`model_kwargs` 是"覆盖"而非"完整指定"**：列出的键覆盖 checkpoint 自带 `config.json`，没列出的键**静默继承**。从官方 checkpoint 续训尤其危险（[§8.2](#82-warm-start-起点选择)）。
- **processor 不从 checkpoint 目录加载**：`train.py::_build_processor` 里 `AutoProcessor.from_pretrained` 分支是**注释掉的**，实际完全由 YAML 的 `processor_kwargs` 构建。两个后果：(1) 别人 checkpoint 里的 `norm_stats` 不会被误用（好事）；(2) 它附带的 tokenizer 也不会被使用，离线 tokenizer 补丁仍然必须。
- **图像增强默认就开着**：`image_transforms is None` 时默认值是 `default_224_head_aug` / `default_224_wrist_aug`。head 的增强链是 `resize_with_pad → random_resized_crop(scale 0.95) → rotation ±5° → color_jitter → rescale[-1,1]`，wrist 少了 crop 与 rotation。**不写这一项 ≠ 没有增强。**
- **`remove_image_padding` 作用在图像 token 上，不是像素**：`img_emb[:, start:end]`，默认 `[48, 208]` 表示从 256 个 image token 里取中间 160 个，剔除 `resize_with_pad` 造成的黑边 token。框架默认即如此。
- **`normalization_mode` 换模式不需要重算 norm**：`norm_stats.json` 里 `mean/std/q01/q99/min/max` 一次性全存，模式只决定用哪几个字段。但**换配置文件名就要换 norm 目录**，同一数据集可直接 `cp -r` 过去。
- **官方 checkpoint 可直接当微调起点**：`pi05_pnp/checkpoint-100000` 与 `pi05_base_bfloat16` 张量名完全一致（812 个），只多 `paligemma_with_expert.paligemma.lm_head.weight`（bf16 下 257152×2048 = 1.05G，正好解释体积差）。

### 13.6 方法层面（最重要）

- **⚠️ 先确认"要学的东西在观测里"，再谈任何训练方法。** 仿真侧为此白跑了三轮训练：换起点、调步数与学习率、数据从 137 条扩到 296 条、物体分布拉宽 5.5 倍——**全部无效**，因为观测里根本没有物体位置信息。任何微调方法都学不出输入里不存在的映射。见 [§4.6](#46-观测信息量自检真机版必做)。
- **警惕"专家用了模型看不到的信息"。** 真机版就是"操作者用了相机没拍到的信息"。写/做演示时逐项自问：**它用到的每个量，模型能从观测里拿到吗？**
- **成功率为 0 时先分离"模型"与"链路"。** 仿真侧同时存在 4 个独立链路故障，每个都能单独造成 0%。按 [§12.1](#121-排障顺序照这个走能省很多时间) 的顺序查。
- 微调方法由"数据量 × 显存"决定，小数据别上重方法——成立，但优先级排在上面三条之后。

**每帧图像的解码方式**：`images_dict/<cam>/rgb` 是所有帧 JPEG 拼接成的一维字节流，用 `rgb_size` 逐帧切片：

```python
offsets = np.concatenate([[0], np.cumsum(rgb_size)]).astype(int)
frame_bytes = rgb[offsets[i]:offsets[i+1]]
img = cv2.imdecode(np.frombuffer(frame_bytes, np.uint8), cv2.IMREAD_COLOR)   # BGR
```

## 附录 C：仿真侧经验摘要

完整记录见 `pi05微调完整指南_仿真版.md` 与项目根目录 `HANDOFF.md`。三条最值钱的：

1. **v1/v2/v3 三版模型闭环成功率全 0%，根因不是模型也不是超参**，而是"观测里没有物体位置信息"——采集时头部相机跟踪目标球，头部朝向既没记进 hdf5、转换时又被写死成 `[0,0]`，两条路同时断掉。留一法实测：只用像素位置反解球位 16.23cm，常数基线 16.39cm，**信息量等于零**。修复后降到 1.63cm。
2. **评测侧同时藏了 4 个独立故障**，每个都能单独造成 0% 成功率：RTC 跨请求污染（预测误差 34.4cm → 0.31cm）、`exec-steps=8` 起步死锁、容器缺 `MUJOCO_GL=egl` 导致三相机全黑、`infer.sh` 硬编码 GPU 0。**这就是"先分离模型与链路"这条纪律的由来。**
3. **仿真环境状态会污染。** 连续跑十余天 + 多次 `pkill` 中断运动后，起始关节跑到 ±6.28 rad、夹爪空载力矩标定漂移，采集成功率从 98.7% 掉到 0%，而日志只写 `success=False`。**正式采集前重启仿真进程。** 真机上的对应纪律是：每批采集前确认机器人回零、标定正常。

仿真侧的诊断脚本（`eval/` 目录）思路可移植到真机，但协议要从 sync 改成 async：

| 脚本 | 作用 | 真机移植 |
|---|---|---|
| `head_info_check.py` | 判观测里有没有物体位置信息 | ⭐ 思路直接可用，见 [§4.6](#46-观测信息量自检真机版必做) |
| `replay_check.py` | 拿训练帧回放，分离模型/链路问题 | 要改成 sender/receiver 协议 |
| `obs_probe.py` | 对比推理端与训练端的观测分布 | 思路可用 |
| `openloop_replay.py` | 开环重放演示动作，隔离执行链路 | 要改成走 SDK 下发 |
